# External Database Compatibility

HBMAME and FinalBurn Neo carry entries for our games. This page records which
of our builds each entry describes, why several no longer match what we ship,
and how new versions reach the maintainers. The comparison is generated by
`tools/rom_registry.py` (section 7 of `docs/qa/ROM_INTEGRITY_REPORT.md`) from
the database sources it reads into `releases/external/`:

| Database | Source file read | Snapshot |
|---|---|---|
| HBMAME | `src/hbmame/drivers/neogeohb.cpp` (master) | `releases/external/hbmame.json`, 2026-10-28 |
| FinalBurn Neo | `src/burn/drv/neogeo/d_neogeo.cpp` (master) | `releases/external/fbneo.json`, 2026-10-28 |

Refresh with
`python3 tools/rom_registry.py --external hbmame=<neogeohb.cpp> fbneo=<d_neogeo.cpp>`.

ROM file names differ by database: HBMAME uses `<id>.<part>` (`779.p1`),
FinalBurn Neo `<set>-<part>.<part>` (`skylance-p1.p1`; `shadowlf_p1.p1`), our
packages `<id>-<part>.<part>` (`779-p1.p1`). Emulators match by size and
CRC32/SHA-1, so the names never need to change.

Only one entry, HBMAME `nosignal`, still describes the file we ship under the
same name. Every other mismatch has the same cause: the release was rebuilt
in place after the database maintainers took their copy (see
`VERSIONING_POLICY.md`). No ROM will be changed to match an old database
hash.

## Proposed updates

`tools/rom_registry.py` writes `releases/db-submissions/<game>_<version>.txt`
for every set whose entry no longer describes our current build. Each file
holds, per database, the changed ROMs (old and new size and CRC), the
database's own entry with the new sizes, CRC32s and SHA-1s substituted, and
the title line with the new version:

| File | Sets | Version proposed |
|---|---|---|
| `skylance_v2.0.1.txt` | HBMAME and FBNeo `skylance` | Sky Lance v2.0.1 |
| `maiya_v4.0.1.txt` | HBMAME and FBNeo `maiya` | Maiya v4.0.1 |
| `shadowleague_v3.0.1.txt` | HBMAME and FBNeo `shadowlf` | Shadow League v3.0.1 |
| `sevenwonders_v1.0.1.txt` | HBMAME `7wonders` | Seven Wonders v1.0.1 |
| `maiyaluna_v2.0.1.txt` | HBMAME `maiyaluna` | Maiya & Luna v2.0.1 |
| `nosignal_v3.0.1.txt` | HBMAME `nosignal` | No Signal v3.0.1 |
| `mahjong_demo_v1.0.1.txt` | HBMAME `mahjongd` | Mahjong Demo v1.0.1 |

Submit them only after the matching version is released on GitHub with the
same bytes (`tools/rom_registry.py --verify` passes and the registry entry
shows the GitHub tag). The maintainers decide whether a set is updated in
place or the old build is kept as a clone; both keep working because each
version has its own hashes. Nothing here edits a third-party database.

## Old and new builds

Every build listed above, current or replaced, is in
`releases/rom-registry.json` with the hashes of each ROM, the commit that
produced it, its SDK version and where it was published, so a player's set
can be identified from its CRCs alone:

```
python3 -c "import json,sys; [print(b['prefix'], b['version'], b['build_id'], b['status']) for b in json.load(open('releases/rom-registry.json'))['builds'] for f in b['files'] if f['crc32'] == sys.argv[1]]" ae68c9a1
```
